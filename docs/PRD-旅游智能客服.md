## 1. 背景与目标

### 1.1 背景

旅游行业商品复杂（酒店、机票、景点门票、火车票、汽车票、接送服务等 6 大品类），用户在售前咨询、订单查询、退款售后等环节高度依赖人工客服，存在以下痛点：

- **咨询量大、重复率高**：80% 以上的咨询为标准化查询（订单状态、价格库存、退改规则），人工重复应答效率低。
- **多品类知识门槛高**：客服需同时掌握酒店入住规则、航班退改、景点开放时间等多领域知识，培训成本高。
- **响应时效要求高**：出行场景时间敏感，用户期望秒级响应。

当前已有一套通用电商客服对话引擎（三轨道架构 + Flow 流程管理），但 Flow 和 Action 层均为通用电商场景，无法直接服务旅游行业用户。本项目需将该引擎改造为旅游行业版本，对接旅游数据中台 API，实现旅游商品咨询、订单管理、退款售后等核心场景的智能化。

### 1.2 目标用户

| 用户角色 | 特征描述 | 核心诉求 | 使用场景 |
|---------|---------|---------|---------|
| C 端旅游用户 | 有出行/住宿/游玩需求的个人用户，通过对话窗口咨询 | 快速获取商品信息、查询订单、办理退款 | 出行前查询、行程中查询、售后退款 |
| 系统管理员 | 课程项目评审方 | 验证三轨道对话引擎在旅游行业的落地效果 | 项目答辩演示 |

### 1.3 业务目标与成功指标

| 目标 | 衡量指标 | 目标值 | 监测方式 |
|------|---------|--------|---------|
| 覆盖旅游核心咨询场景 | 意图识别覆盖率 | 覆盖 8 类核心意图 | 测试用例通过率 |
| 准确路由到对应业务流程 | 路由准确率 | >= 90% | 测试集评估 |
| 对接中台真实数据 | API 联调通过率 | 100% 核心接口可用 | 接口测试 |
| 多轮对话流畅 | 槽位收集完成率 | >= 85% | 端到端测试 |

## 2. 需求概述

将通用电商客服引擎改造为旅游行业版本，实现 10 个业务流程对接中台 API，覆盖商品咨询（酒店/景点/交通）、订单查询、退款申请、行程查询、工单提交、商品推荐、转人工等任务轨道场景，辅以旅游 FAQ 知识库（7 类意图）和闲聊兜底。支持全链路 SSE 流式响应和业务对象消息（卡片）自动填槽。

## 3. 功能详细设计

### 3.1 欢迎引导（onboarding）

**功能描述**：用户首次打开对话窗口时，发送欢迎语并介绍可办理的旅游业务。
**用户故事**：作为旅游用户，我希望打开客服时了解助手能帮我做什么，以便快速发起咨询。
**优先级**：P0

**业务规则**：
1. 每次新建会话时自动触发，无需用户输入。
2. 欢迎语需涵盖当前支持的 6 类业务能力（酒店查询、景点查询、交通查询、订单查询、退款申请、转人工）。

**交互流程**：
1. 用户打开对话窗口
2. 系统发送欢迎消息："你好，我是旅游小助手。我可以帮你查酒店、查景点、查机票火车票、查订单、办退款，或者转接人工客服。请问有什么可以帮你？"

### 3.2 商品咨询 — 酒店查询（hotel_search）

**功能描述**：用户可查询指定城市的酒店列表和价格，或查询某家酒店的详情和房型。
**用户故事**：作为旅游用户，我希望通过对话查询目的地酒店及价格，以便快速选定住宿。
**优先级**：P0

**业务规则**：
1. 必须收集：城市（areaId）、入住日期（checkInDate）、离店日期（checkOutDate）。
2. 可选筛选：星级（starRating）、酒店类型（hotelType）、关键字（keyword）。
3. 入住日期必须早于离店日期，否则提示用户修正。
4. 返回结果包含：酒店名称、星级、起步价、地址摘要。
5. 用户追问某酒店详情时，通过 hotelId 查询酒店详情接口返回地址、设施、入住/退房时间、预订规则等。
6. 用户追问房型时，查询房型接口返回每日价格日历和剩余库存。
7. 用户可通过发送酒店卡片（对象消息）直接提供 hotelId，跳过追问。

**槽位定义**：

| Slot | 对应 API 参数 | 必填 | 来源 |
|------|-------------|------|------|
| areaId | areaId | 是 | 文本提取 |
| checkInDate | checkInDate | 是 | 文本提取 |
| checkOutDate | checkOutDate | 是 | 文本提取 |
| starRating | starRating | 否 | 文本提取 |
| hotelType | hotelType | 否 | 文本提取 |
| keyword | keyword | 否 | 文本提取 |
| hotelId | hotelId（路径参数） | 追问时 | 文本提取 / 卡片消息 |

**交互流程**：
1. 用户说"帮我查一下北京的酒店"
2. 系统收集 checkInDate / checkOutDate（如用户未提供，追问）
3. 系统调用中台 `GET /hotels` 接口查询
4. 返回酒店列表（名称、星级、起步价）
5. 用户追问某酒店 -> 调用 `GET /hotels/{hotelId}` 返回详情
6. 用户追问房型 -> 调用 `GET /hotels/{hotelId}/room-types` 返回房型日历

**异常处理**：
| 异常场景 | 处理方式 | 用户提示 |
|---------|---------|---------|
| 入住日期 >= 离店日期 | 提示用户修正 | "入住日期需要早于离店日期，请重新告诉我。" |
| 无符合条件的酒店 | 告知无结果并建议调整筛选 | "该日期段没有找到符合条件的酒店，你可以换个日期或放宽筛选条件试试。" |
| 中台接口超时/异常 | 降级提示 | "系统暂时繁忙，请稍后再试。" |

### 3.3 商品咨询 — 景点查询（scenic_search）

**功能描述**：用户可查询指定城市的景点列表和门票价格，或查询某景点的详情和票种。
**用户故事**：作为旅游用户，我希望查询目的地有哪些景点和门票价格，以便规划行程。
**优先级**：P0

**业务规则**：
1. 必须收集：城市（areaId）、游玩日期。
2. 可选筛选：景点类型（scenicType）、等级（grade）、关键字（keyword）。
3. 返回结果包含：景点名称、类型、等级、起步票价、地址。
4. 追问详情时返回开放时间、设施标签、预订规则。
5. 追问票种时返回各票种名称、价格、剩余库存。
6. 用户可通过发送景点卡片直接提供 scenicSpotId。

**槽位定义**：

| Slot | 对应 API 参数 | 必填 | 来源 |
|------|-------------|------|------|
| areaId | areaId | 是 | 文本提取 |
| visitDate | 日期参数 | 是 | 文本提取 |
| scenicType | scenicType | 否 | 文本提取 |
| grade | grade | 否 | 文本提取 |
| keyword | keyword | 否 | 文本提取 |
| scenicSpotId | scenicSpotId（路径参数） | 追问时 | 文本提取 / 卡片消息 |

**交互流程**：
1. 用户说"上海有什么好玩的景点"
2. 系统收集游玩日期
3. 调用 `GET /scenic-spots` 查询
4. 返回景点列表
5. 追问详情 -> `GET /scenic-spots/{scenicSpotId}`
6. 追问票种 -> `GET /scenic-spots/{scenicSpotId}/ticket-types`

**异常处理**：
| 异常场景 | 处理方式 | 用户提示 |
|---------|---------|---------|
| 未提供游玩日期 | 追问日期 | "请问你计划哪天游玩？" |
| 无结果 | 建议调整 | "该日期暂无符合条件的景点，试试其他日期或类型？" |
| 接口异常 | 降级 | "系统暂时繁忙，请稍后再试。" |

### 3.4 商品咨询 — 交通查询（transport_search）

**功能描述**：用户可查询航班、火车、汽车班次信息和价格。三种交通类型共用一个 flow，通过 transportType 槽位区分调用不同的中台 API。
**用户故事**：作为旅游用户，我希望查询从 A 到 B 的交通方式和价格，以便选择出行方案。
**优先级**：P0

**业务规则**：
1. 必须收集：出发城市（departureCity）、到达城市（arrivalCity）、出发日期（departureDate）、交通类型（transportType: flight/train/bus）。
2. 可选筛选：航司/车次（carrier）、舱位/席别（seatClass）。
3. 若用户未明确交通类型，系统追问"你想查机票、火车票还是汽车票？"
4. 返回结果包含：班次号、出发/到达时间、出发/到达站、起步价。
5. 追问详情时通过 departureId 返回舱位/席别价格和剩余库存。
6. 接送服务（transfers）暂不纳入此 flow，用户提及时走闲聊兜底或知识轨道。

**槽位定义**：

| Slot | 对应 API 参数 | 必填 | 来源 |
|------|-------------|------|------|
| departureCity | 出发城市参数 | 是 | 文本提取 |
| arrivalCity | 到达城市参数 | 是 | 文本提取 |
| departureDate | 出发日期参数 | 是 | 文本提取 |
| transportType | 决定调用 flights/trains/buses API | 是 | 文本提取 |
| carrier | 航司/车次筛选 | 否 | 文本提取 |
| seatClass | 舱位/席别 | 否 | 文本提取 |
| departureId | 路径参数（追问详情时） | 追问时 | 文本提取 / 卡片消息 |

**交互流程**：
1. 用户说"帮我查明天北京到上海的机票"
2. 系统解析：transportType=flight, departureCity=北京, arrivalCity=上海, departureDate=明天
3. 根据 transportType 调用对应 API（`GET /flights/search` / `GET /trains/search` / `GET /buses/search`）
4. 返回班次列表
5. 追问某班次详情 -> 调用对应详情接口返回舱位/席别价格

**异常处理**：
| 异常场景 | 处理方式 | 用户提示 |
|---------|---------|---------|
| 无法判断交通类型 | 追问 | "你想查机票、火车票还是汽车票？" |
| 无结果 | 建议调整 | "没有找到符合条件的班次，试试换个日期？" |
| 接口异常 | 降级 | "系统暂时繁忙，请稍后再试。" |

### 3.5 订单查询（order_query）

**功能描述**：用户可查询自己的旅游订单列表和订单详情。
**用户故事**：作为旅游用户，我希望查询我的订单状态和详情，以便掌握出行安排。
**优先级**：P0

**业务规则**：
1. 通过 sender_id 识别用户身份（透传中台 `X-User-Id` 请求头），查询该用户下的订单。
2. 支持按订单状态筛选（statusCode）：待支付、已支付、进行中、已结束、已取消。
3. 支持按订单类型筛选（orderTypeCode）：酒店、景点、机票、火车票、汽车票、接送服务。
4. 返回订单列表摘要：订单号、商品名称、金额、状态、下单时间。
5. 追问详情时通过 orderId 返回：商品明细、出行人、支付信息、优惠券/积分抵扣。
6. 用户可通过发送订单卡片直接提供 orderId，跳过列表直接看详情。

**槽位定义**：

| Slot | 对应 API 参数 | 必填 | 来源 |
|------|-------------|------|------|
| statusCode | statusCode | 否 | 文本提取 |
| orderTypeCode | orderTypeCode | 否 | 文本提取 |
| orderId | orderId（路径参数，追问时） | 追问时 | 文本提取 / 卡片消息 |

**交互流程**：
1. 用户说"查一下我的订单"
2. 系统调用 `GET /orders` 查询用户订单列表
3. 返回最近订单摘要
4. 用户追问某订单 -> 调用 `GET /orders/{orderId}` 返回详情

**异常处理**：
| 异常场景 | 处理方式 | 用户提示 |
|---------|---------|---------|
| 用户身份无效 | 提示 | "请先登录后再查询订单。" |
| 无订单 | 告知 | "你当前没有符合条件的订单。" |
| 订单号不存在 | 提示 | "没有找到该订单号，请确认是否正确。" |

### 3.6 退款申请（refund_request）

**功能描述**：用户可对已支付的旅游订单发起退款申请。
**用户故事**：作为旅游用户，我希望通过对话提交退款申请，以便快速办理退改。
**优先级**：P0

**业务规则**：
1. 必须收集：订单号（orderId）、退款原因（refundReason）。
2. 系统需验证订单属于当前用户且状态允许退款（已支付/进行中/已完成）。
3. 需检查是否存在进行中的退款申请（pending/approved 状态），有则拒绝重复提交。
4. 退款金额不能超过订单明细剩余可退金额。
5. 提交后返回退款申请单号和状态。
6. itemId 从订单详情接口中自动获取，无需用户输入。

**槽位定义**：

| Slot | 对应 API 参数 | 必填 | 来源 |
|------|-------------|------|------|
| orderId | 路径参数 | 是 | 文本提取 / 卡片消息 |
| refundReason | body 参数 | 是 | 文本提取 |
| itemId | 路径参数（从订单详情自动获取） | 是 | 系统自动填充 |

**交互流程**：
1. 用户说"我要退款"
2. 系统收集 orderId
3. 系统验证订单可退 -> 调用 `GET /orders/{orderId}` 检查状态
4. 收集 refundReason
5. 调用 `POST /orders/{orderId}/items/{itemId}/refund-requests` 提交
6. 返回退款申请结果

**异常处理**：
| 异常场景 | 处理方式 | 用户提示 |
|---------|---------|---------|
| 订单状态不允许退款 | 拒绝并说明 | "该订单当前状态不支持退款，仅已支付/进行中的订单可申请退款。" |
| 存在进行中的退款申请 | 拒绝 | "该订单已有进行中的退款申请，请勿重复提交。" |
| 退款金额超限 | 拒绝 | "申请金额超过可退余额。" |
| 订单不属于该用户 | 拒绝 | "未找到该订单，请确认订单号是否正确。" |

### 3.7 行程查询（itinerary_query）

**功能描述**：用户可查询即将出行的行程信息（酒店入住、航班出发、景点游玩等）。
**用户故事**：作为旅游用户，我希望查看我的出行行程安排，以便掌握出行细节。
**优先级**：P1

**业务规则**：
1. 无需收集槽位，直接通过 sender_id 查询用户状态为"已支付"或"进行中"的订单。
2. 根据订单类型提取行程关键信息：
   - 酒店：入住/离店日期、酒店名称、房型
   - 机票：航班号、出发/到达时间、出发/到达机场
   - 火车票：车次、出发/到达时间、席别
   - 景点：游玩日期、景点名称、票种
3. 按出行时间排序展示。

**槽位定义**：无需用户输入槽位，sender_id 从会话上下文自动获取。

**交互流程**：
1. 用户说"我最近的行程是什么"
2. 系统调用 `GET /orders?statusCode=paid&in_progress` 查询
3. 提取行程信息并格式化返回

**异常处理**：
| 异常场景 | 处理方式 | 用户提示 |
|---------|---------|---------|
| 无即将出行的订单 | 告知 | "你当前没有待出行的订单。" |
| 接口异常 | 降级 | "系统暂时繁忙，请稍后再试。" |

### 3.8 工单提交（ticket_submit）

**功能描述**：用户遇到服务问题、投诉或需要人工介入时，通过多轮对话提交工单，系统记录并生成工单编号。
**用户故事**：作为旅游用户，我希望在遇到问题时能提交工单，以便有人跟进处理。
**优先级**：P1

**业务规则**：
1. 必须收集：工单类型（ticketType: after_sale/complaint/refund）、关联订单号（orderId）、问题描述（problemDescription）。
2. 工单创建后生成唯一工单编号（格式：WO + yyyyMMddHHmmss + 序号）。
3. 返回工单编号和预计处理时间（24 小时内）。
4. 工单数据本地持久化存储（独立数据库，中台无工单 API）。
5. 工单记录需支持日志审计。

**槽位定义**：

| Slot | 说明 | 必填 | 来源 |
|------|------|------|------|
| ticketType | after_sale / complaint / refund | 是 | 文本提取 |
| orderId | 关联订单号 | 是 | 文本提取 / 卡片消息 |
| problemDescription | 问题描述 | 是 | 文本提取 |

**交互流程**：
1. 用户说"我要投诉"或系统识别为工单意图
2. 系统确认 ticketType（售后/投诉/退款）
3. 收集 orderId
4. 收集 problemDescription
5. 创建工单 -> 本地存储
6. 返回"工单已创建，编号 WOxxxxx，预计 24 小时内处理。"

**异常处理**：
| 异常场景 | 处理方式 | 用户提示 |
|---------|---------|---------|
| 订单号不存在 | 提示确认 | "未找到该订单号，请确认是否正确。" |
| 问题描述过于简短 | 引导补充 | "请再详细描述一下遇到的问题，以便我们更快处理。" |
| 存储失败 | 降级处理 | "工单创建失败，请稍后再试或转接人工客服。" |

**交互流程**：
1. 用户说"推荐几家三亚的酒店"
2. 系统回复："暂未接入智能推荐系统，不过我可以帮你查询三亚的酒店列表，你要试试吗？"

### 3.10 转人工客服（human_handoff）

**功能描述**：用户无法通过机器人解决问题时，转接人工客服。
**用户故事**：作为旅游用户，我希望在机器人无法解决时转接人工，以便获得帮助。
**优先级**：P0

**业务规则**：
1. 用户可随时通过说"转人工"触发，或系统连续 N 次无法识别意图时主动建议。
2. 转接前记录当前对话上下文摘要，便于人工客服接手。

**交互流程**：
1. 用户说"转人工"或系统判断无法处理
2. 系统回复"好的，正在为你转接人工客服，请稍候。"

**异常处理**：
| 异常场景 | 处理方式 | 用户提示 |
|---------|---------|---------|
| 人工客服不在线 | 留言提示 | "当前人工客服不在线，已为你记录问题，工作时间内会有人回复。" |

### 3.11 FAQ 知识库（知识轨道）

**功能描述**：回答旅游行业常见问题，如退改规则、入住须知、证件要求等。
**用户故事**：作为旅游用户，我希望快速了解旅游相关规则和常识，以便做出决策。
**优先级**：P1

**业务规则**：
1. 覆盖 7 类 FAQ 意图：

| 知识意图 | 覆盖内容 | 示例问题 |
|---------|---------|---------|
| faq_hotel_policy | 入住/退房时间、加床政策、取消规则 | "几点退房？""能加床吗？" |
| faq_scenic_policy | 开放时间、儿童/老人票规则、入园须知 | "景点几点开门？""小孩要买票吗？" |
| faq_flight_policy | 退改签规则、行李额度、值机流程 | "机票能退吗？""行李能带多少？" |
| faq_train_policy | 退改规则、改签流程、儿童票规则 | "火车票怎么改签？" |
| faq_payment | 支付方式、发票开具 | "支持微信支付吗？""怎么开发票？" |
| faq_document | 证件要求 | "住酒店要带什么证件？" |
| faq_general | 其他通用旅游常识 | "旅游保险有必要买吗？" |

2. 每类 FAQ 提供结构化知识内容作为 context，由 LLM 润色生成自然语言回答。
3. 回答需保持旅游助手人设，准确且简洁。

**交互流程**：
1. 用户问"机票能退吗"
2. TurnPlanner 识别为知识轨道意图（faq_flight_policy）
3. KnowledgeHandler 匹配 FAQ 内容，交由 LLM 润色生成回答

### 3.12 闲聊兜底（闲聊轨道）

**功能描述**：对不属于任务轨道和知识轨道的输入，进行友好回应。
**用户故事**：作为旅游用户，我希望助手能友好回应非业务问题，体验自然流畅。
**优先级**：P1

**业务规则**：
1. 闲聊回复需保持旅游助手人设，语气友好专业。
2. 可在闲聊中自然引导回业务能力："这个问题我不太擅长，不过我可以帮你查酒店、机票、订单哦。"

### 3.13 对话交互能力

**功能描述**：系统需具备完整的对话交互能力，包括多种消息类型、全链路流式响应和会话管理。
**优先级**：P0

**业务规则**：
1. **文本消息**：支持接收用户文本输入，由 LLM 提取意图和槽位。
2. **业务对象消息（卡片）**：支持接收业务对象消息（如旅客发送一个订单卡片或产品对象）。收到时自动提取对象字段并匹配当前任务所需的槽位，跳过对应的 collect step。
3. **非流式响应**：支持 `POST /api/chat` 一次性返回完整回复。
4. **全链路 SSE 流式响应**：支持 `POST /api/chat/stream`，在处理过程的每个阶段推送进度事件：
   - 意图识别阶段：推送"正在理解你的需求..."
   - Action 执行阶段：推送"正在查询酒店..."等进度提示
   - LLM 回复阶段：逐字推送生成的回复内容
   - 完成事件：推送结束标记
5. **会话管理**：支持创建新会话、获取会话历史消息、获取当前会话状态（当前激活的 flow、已收集的槽位）。
6. **会话持久化**：会话状态持久化存储，支持会话恢复。
7. **意图澄清**：当系统无法准确判断用户意图时（多意图冲突、输入过于模糊、关键信息缺失、与当前上下文冲突），主动向用户澄清。

|------|------|---------|
